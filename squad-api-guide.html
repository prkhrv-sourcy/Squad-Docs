Run the commands in one Bash session, in the numbered workflow below. Stop on any error before proceeding to later steps. Requirements: curl with --fail-with-body support, jq, and uuidgen. The guide makes no network requests and contains no real credentials. Create/update/cancel commands change data when you run them; use a test request and its published quotation.

BASH
export SQUAD_BASE_URL='http://localhost:8083'
export SR_ID='4844'  # Replace with your TEST request number or request UUID.
export SQUAD_EXAMPLE_DIR="$(mktemp -d)"
# For another deployment, replace SQUAD_BASE_URL with its origin (no trailing /).
# Production origin after deployment: https://squad.sourcy.ai

The default is Squad’s local frontend/API proxy port. Change the origin to match the environment you signed into. Tokens must belong to that environment’s Supabase project. Sample names, addresses, supplier IDs and product IDs below are illustrative; replace them with the selected quotation’s data.

1. Authentication and tokens

Current flow: Google sign-in → Supabase user access token → Squad verifies the user and active employee record. Every order endpoint uses Authorization: Bearer <access_token>. There is no Squad password-login endpoint or client-credentials token endpoint for Orders.

  1. Open the chosen Squad environment and sign in with your active Sourcy employee Google account.
  2. Open browser Developer Tools → Network, then reload Squad. Select the /api/session request.
  3. Under Request Headers, copy the Authorization value. Use only the access token after “Bearer ”. Do not copy cookies, refresh tokens or an OAuth provider token.
  4. Paste the token into the hidden terminal prompt below, then call /api/session to confirm access.
BASH
printf 'Paste the access token (without Bearer): '
IFS= read -r -s SQUAD_TOKEN
printf '\n'
export SQUAD_TOKEN

curl --fail-with-body --silent --show-error \
  "$SQUAD_BASE_URL/api/session" \
  -H "Authorization: Bearer $SQUAD_TOKEN"

Expected HTTP 200: schemaVersion, user, email, employeeId, department, avatarUrl. The token is a short-lived user credential, not a permanent API key. Do not put it in this document, source control, chat messages or Brain’s long-running configuration. When the API returns 401, sign in again or let the Squad browser session refresh, then copy a current token. No token refresh endpoint is exposed by Squad itself.

CredentialCan it authorize Orders?
Google/Supabase user access token for an active employeeYes, for its own environment
Supabase publishable/anon keyNo; it only bootstraps sign-in
Supabase secret/service-role keyNo; keep this server-only, do not send it as an employee token
Existing Brain service token for /internal/v1 escalation routesNo; those routes have a different authentication gate
Customer token or non-Google identityNo; active employee and Google identity checks apply

The signed-in employee becomes the audit actor. The optional by object describes who requested the order; it does not authenticate the caller or replace the audit actor.

BASH
curl --fail-with-body --silent --show-error "$SQUAD_BASE_URL/api/health"
curl --fail-with-body --silent --show-error "$SQUAD_BASE_URL/api/auth/config"

Request :id accepts a legacy request number, such as 4844, or a Supabase request UUID. Order :id is an order UUID. These are different identifiers. Paths use the Squad origin with /api; do not substitute the older sourcing-logic /squad/v1 prefix.

Write headers: Authorization, Content-Type: application/json, and a UUID Idempotency-Key. PATCH and DELETE also require expected_updated_at in the JSON body. Keep that timestamp exactly as returned; do not round or reformat it.

3. GET quotation choices

GET /api/requests/:id/order-options — returns {quotations: [{id, generated_at, quote_type, items}]}. HTTP 200 can contain an empty quotations array if the request exists but has no published quote; a missing request returns 404. The items are product/supplier choices, not orders.

BASH
curl --fail-with-body --silent --show-error \
  "$SQUAD_BASE_URL/api/requests/$SR_ID/order-options" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  -o "$SQUAD_EXAMPLE_DIR/quotations.json"

jq '.quotations[] | {id, generated_at, quote_type, items}' \
  "$SQUAD_EXAMPLE_DIR/quotations.json"

# Use the first returned quote for this example. Choose the intended quote in real use.
export QUOTATION_ID="$(jq -er '.quotations[0].id' "$SQUAD_EXAMPLE_DIR/quotations.json")"

Stop if there is no published quotation. Copy the chosen product/supplier snapshots into the create body below. Choice quantities default to 1; price and minimum quantity are deliberately null, so a displayed quote amount is not treated as a confirmed order price.

4. GET all orders

GET /api/orders — returns {schemaVersion, orders, hasMore}. Each row is one order with every item, not one sourcing-request summary.

BASH
curl --fail-with-body --silent --show-error --get \
  "$SQUAD_BASE_URL/api/orders" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  --data-urlencode "requestId=$SR_ID" \
  --data-urlencode 'type=sample' \
  --data-urlencode 'status=requested' \
  --data-urlencode 'page=1' \
  -o "$SQUAD_EXAMPLE_DIR/orders.json"

jq '{hasMore, orders}' "$SQUAD_EXAMPLE_DIR/orders.json"
Query parameterValues / behavior
requestIdOptional exact request number or request UUID; not a free-text search
typeOptional sample or bulk; omit for both
statusOptional value from the status list below; omit for all, including cancelled
pageOptional integer 1–100000; default 1. Fixed page size: 25

Results sort by created_at descending, then id descending. Request the next page while hasMore is true. There is no total count or perPage parameter. Always iterate orders and then every order.items entry.

5. GET orders for one request

GET /api/requests/:id/orders — returns {orders, hasMore}. The path fixes the request; optional type, status and page filters behave as above. An empty list means no matching orders; this endpoint does not separately verify that the parent request exists.

BASH
curl --fail-with-body --silent --show-error --get \
  "$SQUAD_BASE_URL/api/requests/$SR_ID/orders" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  --data-urlencode 'page=1' \
  -o "$SQUAD_EXAMPLE_DIR/request-orders.json"

jq '.orders[] | {id, order_type, status, destination, items}' \
  "$SQUAD_EXAMPLE_DIR/request-orders.json"

6. POST create an order

POST /api/requests/:id/orders — creates the order and every item in one transaction. Returns HTTP 201 with {order}. Run after the quotation-choice step. New items must not supply their own id.

BASH
jq -n --arg quotation_id "$QUOTATION_ID" '{
  order_type: "sample",
  quotation_id: $quotation_id,
  destination: {country_code: "ID", city: "Jakarta"},
  notes: "Tote bag: Navy blue\nBottle: No logo\n\nRecipient: Example Buyer\nCompany: Example Co\nStreet: Example Street 1\nPostcode: 12345\nPhone: +62000000000",
  items: [
    {
      item_name: "Tote bag", product_name: "Cotton tote",
      supplier_id: "supplier-a", supplier_name: "Example Supplier A",
      platform: "1688", platform_product_id: "example-product-a",
      product_url: "https://example.com/tote", image_url: "https://example.com/tote.jpg",
      quantity: 2, unit_price_usd: null, moq: null
    },
    {
      item_name: "Bottle", product_name: "Steel bottle",
      supplier_id: "supplier-b", supplier_name: "Example Supplier B",
      quantity: 1
    }
  ],
  by: {name: "Example Buyer", email: "buyer@example.com"}
}' > "$SQUAD_EXAMPLE_DIR/create.json"

# Generate once for this operation. To retry, repeat only the curl with the same file/key.
export CREATE_KEY="$(uuidgen)"
curl --fail-with-body --silent --show-error \
  -X POST "$SQUAD_BASE_URL/api/requests/$SR_ID/orders" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $CREATE_KEY" \
  --data-binary "@$SQUAD_EXAMPLE_DIR/create.json" \
  -o "$SQUAD_EXAMPLE_DIR/created.json"

jq '.order' "$SQUAD_EXAMPLE_DIR/created.json"
export ORDER_ID="$(jq -er '.order.id' "$SQUAD_EXAMPLE_DIR/created.json")"

For a bulk order, set order_type to bulk and use the required quantities. quotation_id is optional in the API: if omitted, creation chooses the newest published quote by generated_at, created_at and id. Supplying it explicitly avoids choosing an unintended quote type. A supplied quote must belong to the same request and be published.

8. PATCH update an order

PATCH /api/orders/:id — returns HTTP 200 with {order}. All order fields are optional except expected_updated_at. You can change order_type, status, notes, by, destination and items. You cannot move the order to another request or quotation through this endpoint.

This example keeps all existing items and their IDs, changes only the Tote bag quantity, and updates delivery, notes and status. Run the GET-one step immediately before preparing this edit.

BASH
jq '.order | {
  expected_updated_at: .updated_at,
  status: "reviewing",
  destination: {country_code: "ID", city: "Bandung", city_id: null},
  notes: "Tote bag: Navy blue, three pieces\nBottle: No logo\n\nRecipient: Example Buyer\nStreet: Example Street 2",
  items: (.items | map(if .item_name == "Tote bag" then .quantity = 3 else . end))
}' "$SQUAD_EXAMPLE_DIR/current.json" > "$SQUAD_EXAMPLE_DIR/update.json"

export UPDATE_KEY="$(uuidgen)"
curl --fail-with-body --silent --show-error \
  -X PATCH "$SQUAD_BASE_URL/api/orders/$ORDER_ID" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $UPDATE_KEY" \
  --data-binary "@$SQUAD_EXAMPLE_DIR/update.json" \
  -o "$SQUAD_EXAMPLE_DIR/updated.json"

jq '.order' "$SQUAD_EXAMPLE_DIR/updated.json"
  • Omit items for a status-, notes-, destination- or requester-only edit. If items is supplied, it is the complete desired list, not a list of changes.
  • Keep each existing item id to edit it. Omit an existing item from the list to remove it. Add a row without id to create a new item. IDs from another order and repeated IDs are rejected.
  • Every supplied item needs item_name and quantity. Omitted optional snapshot fields on existing items are preserved; explicit null clears optional values.
  • When destination is supplied, send both country_code and city. city_id is optional: it is retained for an unchanged destination and cleared if the city/country changes without a supplied city_id.
  • Partial by updates preserve omitted name/email values. Empty notes may be an empty string or null. Historical null quantity/country/city may remain null, but an existing known required value cannot be cleared.
  • Cancelled orders cannot be edited or reopened. Order status is a recorded workflow value; changing it does not issue an invoice, collect payment or create a shipment.

9. DELETE cancel an order

DELETE /api/orders/:id — returns HTTP 200 with {order}; the returned order has status cancelled. This is cancellation, not physical deletion. Items, quotation links and audit history remain. This example cancels the test order created above.

BASH
# Read the current version before this new cancellation operation.
curl --fail-with-body --silent --show-error \
  "$SQUAD_BASE_URL/api/orders/$ORDER_ID" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  -o "$SQUAD_EXAMPLE_DIR/before-cancel.json"

jq '{expected_updated_at: .order.updated_at}' \
  "$SQUAD_EXAMPLE_DIR/before-cancel.json" > "$SQUAD_EXAMPLE_DIR/cancel.json"

export CANCEL_KEY="$(uuidgen)"
curl --fail-with-body --silent --show-error \
  -X DELETE "$SQUAD_BASE_URL/api/orders/$ORDER_ID" \
  -H "Authorization: Bearer $SQUAD_TOKEN" \
  -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $CANCEL_KEY" \
  --data-binary "@$SQUAD_EXAMPLE_DIR/cancel.json" \
  -o "$SQUAD_EXAMPLE_DIR/cancelled.json"

jq '.order | {id, status, items}' "$SQUAD_EXAMPLE_DIR/cancelled.json"

Retrying that exact DELETE with its original key/body replays its saved response. Cancelling an already cancelled order with a new operation key returns 409. There is no hard-delete endpoint.

10. Fields and limits

FieldCreate / update rules
order_typesample or bulk. Required on create; optional on PATCH.
quotation_idOptional UUID on create; same request and published. Not editable.
destinationRequired on create. Shared by all order items.
destination.country_codeTwo letters; trimmed and normalized uppercase. New orders require it.
destination.cityNonblank string, at most 200 characters. New orders require it.
destination.city_idOptional positive safe integer or null; no lookup is required.
items1–100 items on create or when replacing the list. No items[0]-only assumption.
items[].idReturned UUID; use only for existing items on PATCH.
items[].item_nameRequired nonblank name; maximum 500 characters.
items[].quantityPositive integer up to 2147483647; required on new items. Historical null can be preserved on edit.
items[].product_name / supplier_id / supplier_nameOptional string or null; each at most 2000 characters.
items[].platform1688, alibaba, null, or omitted.
items[].platform_product_id / product_url / image_urlOptional string or null; each at most 2000 characters.
items[].unit_price_usdOptional finite nonnegative number or null. Missing is not zero.
items[].moqOptional positive integer up to 2147483647 or null.
notesOptional free text or null, at most 5000 characters; line breaks are preserved.
by.name / by.emailOptional requester details. Name ≤2000 characters; valid email ≤320 characters, or null.
statusPATCH only. Allowed values listed below.
expected_updated_atRequired PATCH/DELETE timestamp from the last read, including full precision.

Statuses: requested, reviewing, quoted, invoiced, paid, processing, shipped, completed, cancelled. PATCH can also set cancelled; DELETE is the dedicated cancellation operation. Both leave cancelled orders read-only.

Sample quantity defaults to one and is capped at three per new item by the UI. The backend does not enforce a sample-specific cap. Bulk has no UI business cap; the database integer limit still applies.

Recipient, company, street, postcode and phone remain lines in notes; there are no structured address fields for them. Sample fees, voucher credits, payable estimates and delivery charges are not stored by this order contract. Do not derive confirmed invoice totals from missing values. Unknown body keys are rejected; send only documented fields.

11. Retries and errors

  1. Generate a fresh UUID once for each intended create, update or cancellation. Store it with the exact body and target request/order before sending.
  2. If the connection times out or a retryable 5xx occurs, resend the same method, path, body and Idempotency-Key. Do not generate a new key just because the outcome is uncertain.
  3. The same key and identical operation returns the stored successful response. Reusing a key for different input, target, action or audit actor returns 409.
  4. For an edit-version conflict, GET the latest order and reconcile the change. Only then submit a new operation with its latest updated_at and a fresh key. Do not blindly overwrite the newer order.
  5. On a genuine new operation, generate a new key. Refresh authentication on 401. Retry transient read failures with bounded backoff.
HTTPMeaningAction
400Malformed JSON, invalid fields/IDs, missing retry key or invalid quotationFix the request. Do not retry it unchanged.
401Missing, invalid or expired user tokenObtain a current employee access token.
403Non-Google user or not an active employeeUse an authorized employee identity.
404Order/request/route not foundCheck the identifier and that this deployment contains the endpoint.
409Stale updated_at, cancelled order, or reused key with different inputRead the message and reconcile; do not automatically overwrite.
503Auth/employee-directory or order storage unavailable, or missing configuration/migrationCheck deployment/configuration; retry transient failures with the original write key/body.
JSON
{
  "error": "order_error",
  "message": "This order changed. Refresh it before saving again"
}

Response wrappers differ: GET /api/orders includes schemaVersion; request-scoped lists contain orders and hasMore; detail/mutation endpoints contain order. Do not require schemaVersion on every response. The current paths are not URL-versioned.

12. How Brain can integrate

Today: an authorized developer can use the employee-token examples to test the contract after deployment. Unattended Brain order calls are not ready: these /api routes do not accept the existing Brain service credential, and there is no Orders service-token issuance flow. Do not solve this by retaining a person’s access/refresh token or sharing Squad’s database key.

PhaseBrain workSquad work
Contract work nowBuild a client around the seven endpoints; iterate all items; preserve nulls and multiline notes; persist retry keys and timestamps. Use contract mocks until deployed.Keep this guide and the request/response schemas aligned.
Enable automation nextStore the agreed service credential server-side and implement its rotation.Add explicit service authentication for Orders, approved read/write scopes and a stable machine audit identity. Define and document credential provisioning; do not impersonate an employee.
After deployment and service authCall Squad over HTTPS; test create → read → update → cancel against a dedicated test request. Reconcile 409s and retry ambiguous writes safely.Publish the confirmed origin, auth instructions, paths and availability status here.

Data flow after integration: Brain → authenticated Squad order API → Supabase orders + order_items. Squad owns order reads/writes and does not call Brain to perform them. No Brain integration, new service credential or production deployment is created by this documentation task.

Brain should persist order.id, the returned item IDs, updated_at, its operation key and exact request payload. Do not treat the optional by object as an authorization mechanism. Use a deliberate item identifier for edits; the sample update matches the demo item name only for readability.
